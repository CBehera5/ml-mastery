## 1. Governing boundaries

This proposes Python-only module policies. Existing Mathematics/Regression contracts, scoring rules, evidence scopes and notebook bytes remain unchanged. Browser activities are deterministic simulations of author-owned operations; **no arbitrary Python execution, untrusted learner-code execution, user uploads, Python service, AST interpreter or general expression evaluator** is permitted.

Supported constructs below describe **what authored teaching examples may contain**, not a language accepted from learner text. A displayed snippet is immutable except for allowlisted slots. “Fix the bug” means selecting a finite repair/accepted tuple and its explanation, not submitting unrestricted code.

Trusted Python executed in author tests is separately reviewed repository code. It must never concatenate, compile, import, execute, deserialize as code or invoke subprocesses from a learner response. Notebook execution tests run only committed author notebooks/reference cells, never learner-edited notebooks.

## 2. Scope and supported authored operations

### Python subset

Author-owned snippets may use:
- Bounded int/finite float/str/bool/None literals; names, reassignment, ordinary arithmetic + − * / // % ** with exercise-specific finite bounds, comparisons and parentheses.
- if/elif/else; and/or/not and explicit is None checks.
- Lists, tuples, dicts and sets; named keys, membership, len, positive/negative integer indexing and half-open slices.
- for over fixed collections/range, enumerate and zip with explicit lengths; bounded accumulators and empty-count guards.
- def, positional/keyword arguments, return, local scope and simple composition; explicit default-None handling.
- Single-level list/dict comprehensions with one bounded predicate.
- Narrow try/except and explicit raise; preset exception traces.
- Curated import math/json/csv/io examples; context-managed trusted local/embedded CSV/JSON reads in notebooks; a tiny practical class with __init__, instance attributes and one method as introductory recognition/trace material.

No while/recursion/generators, arbitrary comprehensions, closures/decorators/metaclasses/inheritance, dynamic attributes, wildcard imports, reflection, eval/exec/compile, pickle, shell/system calls, sockets/HTTP, dynamic package installation, arbitrary paths, browser file access or learner-defined functions/classes enter browser evaluation. These are teaching/evaluator scope exclusions, not a claim that Python itself prohibits them. Real notebook learners may explore privately, but the platform never receives or grades that code.

## 3. Exercise types and response forms

| Exercise family | Learner response | Deterministic grading |
|---|---|---|
| Predict output/type/error | Option ID, finite numeric field, or finite grid-cell selections; expected type/error code explicit | Exact named type/option/error code; numeric rule below; never stdout repr matching by accident |
| Missing code | Map of slot IDs to allowlisted token/choice IDs | Entire tuple must match an approved accepted tuple; all required slots present, no extras |
| Identify-and-fix bug | Bug-location ID + repair tuple + reason/counterexample ID | All required parts correct; error identification alone is insufficient |
| Shape/broadcasting | Defined/incompatible choice, dimension fields and axis/meaning reason | Exact rank/dimensions and semantics; a legal but wrong-purpose broadcast fails the intent objective |
| DataFrame reasoning | Row/column/key IDs, ordered values/schema or outcome option | Preserve index/column/row order as specified, exact duplicate/null handling and join multiplicity |
| Leakage identification | Fit-row IDs or boundary ID + proposed repair + explanation | Correct information boundary and repair; choosing the word “leakage” alone does not pass |
| Pipeline ordering/evaluation | Ordered finite stage IDs/configuration slots + fit/CV/test rationale | Correct whole pipeline tuple, valid branch types and training/validation/test provenance |

### Safety validation happens before scoring

Proposed bounds for one exercise:
- Author snippet ≤25 lines and ≤4 KiB UTF-8; loop traces ≤32 steps; no unbounded operation.
- Numeric arrays rank 0–2, each nonzero dimension ≤32 and ≤64 cells total (so the 12×4 training feature matrix is supported); table ≤32 rows × 8 columns; UTF-8 strings ≤120 characters per fixture cell. Explicit empty shapes are allowed only in named fixtures. Any oversized output is a supported-size/content limitation, not a claim that NumPy/pandas itself raises an error.
- At most eight transformation stages and eight code slots; at most eight choices per slot and eight accepted whole tuples per definition. Experiments expose at most 64 reviewed configuration IDs per activity; full fixtures cover those 64-or-fewer states, not every Cartesian product of incorrect answer choices.
- Each normalized answer atom ≤512 bytes, ≤8 known fields/slot entries; at most two atoms per family; family payload plus identity ≤1.5 KiB. Module submission ≤64 KiB for at most 32 expected families (≤48 KiB family allocation plus ≤16 KiB envelope headroom). Selection slot IDs ≤16 ASCII characters, option IDs ≤24; definition IDs ≤128. Oversize records fail closed rather than being truncated.
- Numeric source values are finite with |value|≤10^6, integer exponents 0–4 and author-verified intermediates |value|≤10^12. Explicit missing cells use a tagged sentinel, never raw JSON NaN/Infinity; named nonfinite/error outputs are tagged reference outcomes, not valid numeric answers. No arbitrary input expression is accepted.
- At most 32 objective families per independent attempt. Critical families have exactly two scoring atoms: decision/calculation/repair and reason/counterexample; a compound repair may contain several required slots. All required subparts use AND. Unknown, omitted or duplicate atom identities are structural errors; confirmed blank UI answers use the explicit unanswered sentinel.
- Persistence envelope cap remains 256 KiB: latest-20 attempt summaries ≤2 KiB each (≤40 KiB), active draft ≤64 KiB, latest full submitted responses/result ≤64 KiB, evidence/policy references ≤32 KiB and counters/metadata ≤16 KiB. Total allocated ≤216 KiB leaves ≥40 KiB framing headroom. Older full responses are not retained; scores, per-family outcomes, critical failures and original policy identity are retained. No raw snippets or arbitrary learner text. Repeated passes/completions reuse stable version-scoped evidence IDs, preventing unbounded mastery/evidence growth. If a valid future record exceeds its allocation, disable saving with a clear warning; do not silently delete mastery/foreign data to fit.

These limits are draft security/usability requirements, to test with the actual schemas before approval/freeze. Author validation rejects a definition that cannot fit the bounds.

Reject unsupported schema/content/variant IDs; wrong response kind; unknown/duplicate/missing keys; prototype-pollution keys; nonfinite/overflow numbers; invalid shape or out-of-range values; unsupported slot strings; arbitrary Python, import paths, URLs or source text in a code slot; HTML/script markup; oversize/deep payloads; bad encodings and executable serialization. Never resolve a name as a function or property from response text.

No JSON/code editor or answer import is exposed. Native controls construct typed responses. Collection/slot identities are explicit arrays checked for duplicates. New Python persistence envelopes use a specified canonical JSON encoding: bounded parse, strict schema validation and canonical re-encoding must match the original stored bytes, rejecting duplicate JSON members/noncanonical or hand-edited records while preserving them with writes disabled. JSON.parse alone does not detect duplicate members. This rule applies only to new Python keys, never historical Math data. Maximum nesting depth is 8; prototype keys are rejected at every object level. The authoring pipeline must likewise detect duplicate members before accepting a definition.

Distinguish **invalid/unsupported response** from **valid incorrect reasoning**:
- Invalid: no evaluation, no correctness/attempt evidence, no code execution; show a precise bounded-input message and preserve the learner's other valid answers.
- Valid wrong: deterministic conceptual feedback and retry accounting; do not disguise it as a syntax/platform failure.
- Malformed author definition: fail the activity closed with a service/content-unavailable message; never manufacture a zero-output success.
- Browser render escaped text only; no raw HTML from snippets/responses. No mathematical claims from unmatched fixtures.

At confirmed assessment submission, the controller converts blank UI fields to an explicit known-atom **unanswered** sentinel; that is a valid incorrect answer, not an invalid payload. Missing/unknown family or atom IDs in a payload remain structural errors. This Python-local normalization happens before invoking an existing exercise helper and does not change old response contracts. No missing critical response can disappear from the denominator or bypass its gate.

### Deterministic result selection

1. Validate version, shape, IDs, response size/domain and ownership.
2. Resolve only a reviewed definition/fixture and its finite controls.
3. Normalize permitted answer formats, then compare to definition-owned expected values/tuples.
4. Combine atoms within a family using AND. One family is one scored point.
5. Produce outcome, specific feedback, failed objective IDs, targeted remediation and next supported variant. No timestamps/randomness in correctness.
6. Lesson/assessment controller, not the pure evaluator, applies retry/evidence rules.

For bounded experiment controls, use discrete allowed states or author-defined typed operation IDs backed by complete fixtures. Do not expose continuous arbitrary NumPy/pandas programs and pretend a finite fixture set can execute them. A future new pure operation interpreter would require a separate approved architecture.

The numeric absolute-plus-relative comparison needs a Python-local pure adapter: the existing shared numerical evaluator accepts absolute tolerance only. Validate typed numbers first, apply the declared comparison outside React and compose its result into the family; do not modify old numerical contracts or silently drop the relative term. Likewise reject extra slot keys before delegating to the existing constrained-code helper, which is not by itself the full strict Python response validator.

## 4. Equality and equivalent correct answers

- **Options, categories, booleans, types, dimensions, integer counts and IDs:** exact match. Do not coerce True into integer 1 or a numeric-looking string into a number unless conversion is the stated objective.
- **Numeric floating answers:** accept if finite and |actual−expected| ≤ absoluteTolerance + relativeTolerance×|expected|; proposed default 1e−9 for each, with exercise-specific displayed rounding tolerance. UI requests appropriate precision and stores the unrounded expected fixture. A displayed 0.33 must not require an undisclosed 0.333333333333.
- **Arrays:** exact rank/shape/dtype category when assessed, ordered per-cell comparisons, explicit missing mask. Shape (m,) is not (m,1); no flattening to make a wrong answer pass.
- **DataFrames/Series:** compare declared index, columns, order, dtype/missingness and canonical cells, not pandas display strings. Stable group sorting/merge order is explicitly authored. Treat output as unordered only when the exercise declares it so.
- **Missing/nonfinite/error:** tagged values such as {kind:missing}, {kind:undefined,reason:all_missing} or named error class/code. No JSON NaN/Infinity. Missing, zero and exception are never interchangeable.
- **Text:** Unicode normalization/outer whitespace only where explicitly declared; preserve case and meaningful internal whitespace/indentation. Prefer option IDs to free text.
- **Equivalent code:** accepted finite **whole tuples**, e.g. X@w+b and np.matmul(X,w)+b only where both authored templates are explicitly allowed and verified for every fixture. Do not independently accept each slot if a mixed combination is incorrect. Reuse existing constrained-code evaluation for each complete accepted tuple; no changes to old evaluator semantics.
- **Join/group/pipeline alternatives:** accept only explicitly reviewed semantics under the stated column order/nullability/fit provenance. Similar-looking output on one fixture is not proof of equivalence.
- **Charts:** assess exact underlying values, bins/limits, labels/units and claim interpretation. Do not award/deny mastery on pixel similarity, theme, fonts or visual aesthetics.
- **Model output:** tolerance plus shape/schema; evaluation/selection rules fixed before the candidate outputs are shown. Model-comparison ties use a declared tolerance and prefer the simpler baseline, not a hidden arbitrary winner.

Each accepted equivalence needs both positive and counterexample fixtures. Unsupported-but-possibly-correct free code is not called mathematically wrong: explain the bounded format and offer the supported slot choices/notebook practice.

### Completion is separate

A lesson completes after all four objective practice families are correctly demonstrated across available practice variants and a meaningful experiment action plus bounded explanation/prediction. Marking practice completion does not mark objective or module mastery. A module's instructional completion summarizes its lessons; independent assessment availability is not locked behind that summary.

On an independent pass, record module-level mastery and **only the objectives whose independent families were correct**. Missed noncritical objectives remain unmastered with remediation. On a failed module attempt, record the assessed attempt and correct/incorrect results but do not award new mastery. Previously earned mastery remains after later failure, scoped to its original assessment version. No phase-wide automatic credential is proposed.

The label should be “demonstrated bounded Python/ML reasoning” rather than certification of unrestricted coding fluency. Three forms and client-side answers cannot provide high-stakes exam security.

## 7. Retry, feedback and anti-pattern design

### Guided practice
- Predict before reveal. Up to two valid submissions per reference variant; invalid payloads do not consume attempts.
- First valid wrong answer: explain the specific misconception with the relevant trace row; link to its prerequisite/remediation without exposing unrelated answers.
- After second wrong submission: show the worked correction and require the alternate reference for another scored completion opportunity. If both A and B are exhausted, require the targeted remediation walkthrough and its bounded counterexample check, then begin a new explicitly labeled review cycle at A. This is not a third novel variant and cannot award independent mastery. Persist per-variant/per-cycle attempt counters so reload does not reset the allowance; unlimited review cycles avoid a permanent completion deadlock.
- Revealing a solution or toggling options is not completion. Previously earned practice completion remains during later review.
- No timer/paid cooldown. Repeated finite forms are transparently review, not proof of fresh transfer.

### Independent module attempt
- Active → review → explicit confirm submission → results. No answer-by-answer correctness before submission.

## 8. Persistence, resets and migration

Use a strict scope/version loader. Null means new progress. Corrupt, unknown/future, wrong-module or mismatched-version records remain unchanged; show an accessible warning and disable writes.
